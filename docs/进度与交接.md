### 阻塞级缺陷：明文访问下读者端直接报错

点「试跑访谈稿示例」时页面顶部弹出红色错误条 `crypto.randomUUID is not a function`，页面停在原地不跳转，读者无法提交反馈。

根因：`crypto.randomUUID()` 按规范**只在 secure context（HTTPS 或 localhost）暴露**。手机走 `http://172.31.26.77:4199` 这种明文非回环地址，不算安全上下文，该方法为 `undefined`，调用即抛 TypeError。

影响两处，都在 F1 的 `app.js` 里：

| 位置 | 用途 | 症状 |
| --- | --- | --- |
| `app.js:117` | 场景匹配的 `requestId` | 开发者在手机上跑不了匹配 |
| `app.js:151` | 读者反馈的 `submissionId` | 读者提交不了反馈 |

要点：浏览器证书无效的 HTTPS **同样不算** secure context，自签证书救不了这条路。

结论与处置：

- 正式部署走域名 + HTTPS 就没有这个问题（本来也必须走 HTTPS），所以不是上线阻塞。
- `docs/DEPLOY.md` 第 1 节的路线 C（`http://IP:4173`，无备案时的兜底）会直接踩中，**已加前端兜底修复，见下方「修复」小节**。

### 顺带改的服务端

`server.py` 新增 `--host` 参数（等价环境变量 `ZHIYU_HOST`，默认 `127.0.0.1`，默认行为不变），让本机实例能对同网段设备开放。`ZHIYU_HOSTS` 白名单仍然生效：实测 `Host: evil.example` 返回 403，白名单内的 IP 直连返回 200。

### 修复（11/20 12:50，用户选 A 授权）

在 `app.js` 顶部注入兜底：原生 `crypto.randomUUID` 缺失时，用任何上下文都可用的 `crypto.getRandomValues` 补一个 v4 格式的 UUID。只补缺失的方法，不改既有逻辑。

三处关键约束，都写进 `test_frontend_contract.py`（4 组）守着：

1. **补丁只能在 `app.js`，不能内联到 `index.html`** — CSP 是 `script-src 'self'` 且无 nonce，内联脚本会被静默拦掉。
2. **不能给 `globalThis.crypto` 重新赋值** — `window.crypto` 是只读访问器，严格模式下赋值抛 TypeError，整段脚本停摆（页面卡在「正在打开知遇…」）。第一版补丁就踩了这个坑，已修正为只往现有对象上加方法。
3. **两处调用点必须在兜底之后** — `app.js:117`（requestId）与 `:151`（读者 sid）。

验证：Node 生成 1000 个 UUID 全部格式合法且唯一；桌面 Chrome 走同样的明文 IP `http://172.31.26.77:4199`，`typeof crypto.randomUUID === "function"`，点示例按钮成功跳到 `#match/...`，无错误条；反向验证——把兜底条件改成 `if(false)` 后契约测试确实报 FAILED。全量回归 57 组测试 + 30 项黑盒通过。

一个运维坑：静态资源 `Cache-Control: max-age=300`，真机验证时浏览器缓存了旧的坏 `app.js`，改完文件手机仍是旧版，清缓存后才生效。演示前若改过前端资源，记得强刷或加版本查询串。

## 监控与告警（11/20）

规划书 8.8 要求「cron 每 5 分钟探 `/api/health`，连续 3 次失败告警」与「磁盘 80% 告警、每周 `integrity_check`」。这三条此前一条都没落地——`/api/health` 接口有，但没有人定时去看它，服务半夜挂掉要等到有人打开页面才知道。本轮补齐。

新增 `scripts/watch.sh`，一个脚本三种用法：

| 用法 | 由谁调 | 做什么 |
| --- | --- | --- |
| 默认 | cron 每 5 分钟 | 探 `/api/health`、看磁盘余量 |
| `--integrity` | cron 每周日 04:10 | 线上库 `PRAGMA integrity_check` |
| `--reset` | 人工 | 计划维护前清状态，免得结束后收到一条「已恢复」 |

行为按「不制造噪音」设计：

- **三连败才报**。单次丢包不是故障；每次失败都发一条，两周之内所有人都会屏蔽这个群。
- **告警只报一次**。持续故障不重复推送，恢复时补一条「已恢复」并给出中断时长。
- **503 是故障，不是健康**。健康检查在数据库不可用时正好返回 503，读者会看到报错页，所以计入失败；但文案直接指向 `df -h` 与 `--integrity`，而不是让人去查端口。
- **磁盘不做三次去抖**。它不会自己好，低于阈值报一次，回到阈值以上记一次恢复即可。
- **状态文件按 `key=value` 解析并做数字校验**。实测把 `fails=$(id)` 塞进状态文件不会被执行，按非法值归零。

告警去向用 `--notify <命令>`（消息走 stdin），避开主机上没有邮件凭据这件事；没配通知渠道时输出仍进 `var/watch.log` 与 stderr，cron 的 `MAILTO` 能接住。预检 E6 在两种渠道都没有时报 `WARN`——这是演示周最容易漏的一步。

`deploy/crontab` 把四条任务固化成文件，`sudo crontab -u zhiyu deploy/crontab` 一次装完。手写 `crontab -e` 的老做法没有任何复核点，`backup.sh` 丢执行位那次就是这么埋进去的。

预检相应扩到 43 项：A7 的执行位清单加了 `watch.sh` 与 `prune.py`；E 组新增 E4（探活行在不在）、E5（探活地址是不是还留着 `zhiyu.example.com` 占位符、是不是只打回环）、E6（告警有没有去向）。「空 crontab」与「读不到 crontab」分开判定：前者是装漏了报 `FAIL`，后者是权限不足记 `SKIP`。

## 复核与修复（11/20 16:20）

重跑 65 组测试、30 项验收与假主机预检后，又逐项压了监控脚本，发现四个「无人值守时静默失效」的缺陷，均已修，并各有测试守着：

1. **缺值参数让脚本死循环**。`--url` 后面没有值时 `shift 2` 不消费任何参数，`$1` 仍是 `--url`，解析循环永不退出；`watch.sh` 有 12 处、`preflight.sh` 有 4 处同样的写法。放进 cron 就是每 5 分钟挂死一个进程，还不告警。现统一用 `need_value` 判参数个数，缺值立即退出 2。
2. **状态文件写不进去就永远不告警**。`save_state` 静默失败后，每轮都从「第 1 次失败」重新计数，三连败阈值永远达不到——服务挂一周也不会有通知。现改为 `persist`：写不下去就打印原因并退出 2（cron 落进 `watch.out`）；另外把「状态路径是个目录」这种 `mv file dir` 会假装成功的情况显式判失败。
3. **回环探测被代理接管**。主机若设了 `http_proxy`，curl 会把 `127.0.0.1` 交给代理，回的是代理自己的错误页：实测同一地址不带 `--noproxy` 得 502、带上得 000，健康与故障会被反过来判读。`watch.sh`、`preflight.sh` 的 C4、`restore-check.sh` 三处回环调用统一加 `--noproxy 127.0.0.1,localhost,::1`。第一版把 `--noproxy *` 存进变量再展开，`*` 被当成通配符展开成工作目录里的文件名——自己制造了一次故障，已改。
4. **`--disk` 写错等于关掉磁盘监控**。`df` 读不到时原来静默返回，现在报错退出 2。顺带让 `301/302` 给出「探活地址指错了」的文案，而不是让人去 `systemctl status` 查一个其实正常的服务。

测试从 59 组加到 **65 组**：`test_deploy.WatchScript` 3 组（缺值立即退 2、状态不可写必须退 2、回环 curl 必须带 `--noproxy`）、`test_deploy.PreflightDocs` 1 组。反向验证：去掉 `need_value`、把 `persist` 换回 `save_state`、删掉 `--noproxy`、把文档项数改回 43、给脚本多加一项，五种都会 FAILED。

**文档计数错误**：预检项数四份文档都写 43，实际 A7+B9+C6+D6+E6+F5+G3 = **42**，E 组从 3 项扩到 6 项时算错一。已全部改为 42，并让 `PreflightDocs` 从脚本里解析项数去比对四份文档的原句，不再靠手数。

环境注意：本机 `bash` 与 Python 可能不在同一个网络命名空间，绝对 Windows 路径在 shell 里也不成立。测试传给 shell 的路径一律用仓库相对路径——曾因此把临时目录建成仓库内一个名为 `C:` 的目录，已清掉。

## 与规划书的偏差（以此为准）

1. 读限流改为进程内存计数，不落 `limits` 表，重启清零。写限流仍落库。
2. 新增进程内 `WRITE_LOCK`：SQLite 单写者，并发写会偶发 `readonly database`，串行后消失。5 并发 p95 约 100 ms。
3. 会话值校验从 32 字符放宽到 16 至 64 字符：演示工作区的 owner 由 `uid()` 生成，长度 24。
4. 索引改在补列之后创建，否则旧库启动即失败。
5. 恢复码可重复使用，直到轮换；不是一次性凭据。
6. 备份脚本依赖 `sqlite3` 命令行，服务器需安装。
7. 写限流计数独立成一个事务，先提交再处理业务；代价是每个写请求多一次 `BEGIN IMMEDIATE`，5 并发 p95 从约 60 ms 升到约 100 ms。
8. `runs` 增设 90 天留存，被已发布卡片引用的行永久保留。规划书没有定义清理策略，这是本轮补的运维约定，实现在 `server.prune` 与 `scripts/prune.py`。
9. 告警去重靠状态文件，不靠 cron 每 5 分钟发一条：连续 3 次失败报一次，恢复补报一次。规划书只写「连续 3 次失败发邮件或钉钉」，没有定义恢复通知与重复告警，这里按「不制造噪音」定。
10. 通知走 `--notify <命令>`（消息从 stdin 进），不用 SMTP：主机没有发信凭据，团队用的是钉钉群。没配通知渠道时输出落 `var/watch.log`，cron 的 `MAILTO` 可兜底，预检 E6 会提示。
11. 磁盘阈值按「剩余低于 20%」判定，对应规划书「超过 80% 告警」，两者等价；`--disk-min` 可调。磁盘不做三次去抖，因为它不会自己恢复。
