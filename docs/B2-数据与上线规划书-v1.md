## 1. 结论摘要

B2 的目标是让知遇从"本机演示原型"变成"评委可以打开、数据不会丢、出问题能退回"的公网服务。现有原型的数据骨架够用：SQLite 已建项目、运行、卡片、访问、反馈、限流六张表，归属校验、发布快照、版本递增、去重计数都已实现并有测试覆盖。不需要换技术栈，缺的是四件事：

1. 公网可部署性：Host、Origin、Cookie、真实客户端 IP 在当前代码里都按回环地址写死，反向代理后面会直接拒绝请求。
2. 身份可恢复：清 Cookie 即失去工作区，无法给评委提供稳定的测试账号。
3. 日常运维：没有健康检查、进程托管、定时备份和恢复演练。
4. 版本与回退：没有构建标识，冻结后无法判断线上跑的是哪个提交。

工作量估算 58 小时（按每日可投入 4 小时计，约 14 至 15 个工作日），落在 11/20 至 12/07 的窗口内，留约 2 天缓冲。

最大的风险不在代码，在域名与备案。如果已购主机在中国大陆地域，且团队没有已备案的域名，80/443 端口会被拦截，HTTPS 方案必须改道。这件事必须在 11/21 20:00 前定下来，否则 11/29 的公网全链路验收没有退路。

- 对外接口：项目增改、候选选择、卡片发布与公开读取、会话与事件、反馈提交与查询、结果汇总。
- 部署：主机配置、反向代理、TLS、进程托管、持久目录、日志。
- 备份与恢复：定时备份、完整性校验、恢复演练、RPO/RTO 承诺。
- 运行保障：健康检查、监控告警、发布与回退流程、运行说明、测试账号。
- 公共数据结构汇总与联调版本发布（PDF 第 9 页明确归属 B2）。

### 2.2 不由 B2 负责

- 知乎检索、模型排序、证据核对、匹配效果对照（B1）。
- 工作台、试用页、反馈表单、看板的前端实现（F1、F2）。

### 2.3 与其他岗位的分界原则

数据怎么写由 B2 定，数据表示什么含义由 P 复核，匹配相关字段由 B1 复核。前端只依赖 `API.md` 里列出的字段，不直接读数据库。跨模块改动先进契约文档，再改代码。

| 项 | 现状 | 目标 | 影响 |

| 监听地址 | 绑定 `127.0.0.1` | 保持回环，由反向代理对外 | 无，这是正确做法 |

| TLS | 无 | 反向代理自动证书 | 浏览器提示不安全 |
| 备份 | README 写了手动方法 | 定时脚本 + 每周演练 | 数据丢失无法恢复 |
| 版本标识 | 无 | 构建号写入健康检查 | 无法确认线上版本 |
| 日志 | `log_message` 静默 | journald + 访问日志，正文脱敏 | 故障无迹可查 |

### 3.3 可以直接复用的部分

现有 `own()`、`card()`、`fields()`、`limit()` 四个校验函数结构清晰，改造成本低。`BEGIN IMMEDIATE` 已经在写路径上使用，SQLite 的单写者模型配合 WAL 足以支撑本次流量。`test_flow.py` 用临时数据库与独立 Cookie 的写法可以直接扩展成部署测试。

## 5. 数据模型

### 5.1 六类实体与表的对应

PDF 要求建立"项目、任务、候选、卡片版本、会话与反馈"六类数据。当前实现的对应关系如下：

| PDF 实体 | 实际承载 | 说明 |
| --- | --- | --- |
| 项目 | `projects` | 一行一个项目，业务字段存 `data` JSON |
| 任务 | `runs` | 一次匹配请求一行，含状态、错误码、项目快照 |
| 候选 | `runs.data.candidates` | 随运行一起写入，不单独建表，理由见 5.4 |
| 卡片版本 | `cards` | 一行一个不可变快照，`version` 单调递增 |
| 会话 | `visits` + Cookie | 读者会话即 `(slug, reader)`；开发者会话即 `owner` |
| 反馈 | `feedback` | 一行一份，按会话与提交 ID 双去重 |

### 5.2 表结构 v2

在现有六张表上补时间戳与恢复码表，全部为加法迁移，不改动已有列。

```sql
CREATE TABLE IF NOT EXISTS projects(
  id         TEXT PRIMARY KEY,
  owner      TEXT NOT NULL,
  data       TEXT NOT NULL,
  created_at INTEGER NOT NULL DEFAULT 0,
  updated_at INTEGER NOT NULL DEFAULT 0
);
CREATE INDEX IF NOT EXISTS idx_projects_owner ON projects(owner, updated_at DESC);

CREATE TABLE IF NOT EXISTS runs(
  id         TEXT PRIMARY KEY,
  pid        TEXT NOT NULL,
  rid        TEXT NOT NULL,
  data       TEXT NOT NULL,
  created_at INTEGER NOT NULL DEFAULT 0,
  UNIQUE(pid, rid)
);
CREATE INDEX IF NOT EXISTS idx_runs_pid ON runs(pid, created_at DESC);

CREATE TABLE IF NOT EXISTS cards(
  slug         TEXT PRIMARY KEY,
  pid          TEXT NOT NULL,
  version      INTEGER NOT NULL,
  signature    TEXT NOT NULL,
  data         TEXT NOT NULL,
  active       INTEGER NOT NULL DEFAULT 1,
  published_at INTEGER NOT NULL DEFAULT 0,
  UNIQUE(pid, version)
);
CREATE INDEX IF NOT EXISTS idx_cards_pid ON cards(pid, version DESC);

CREATE TABLE IF NOT EXISTS visits(
  slug       TEXT NOT NULL,
  reader     TEXT NOT NULL,
  opened     INTEGER NOT NULL DEFAULT 0,
  first_seen INTEGER NOT NULL DEFAULT 0,
  opened_at  INTEGER,
  PRIMARY KEY(slug, reader)
);
CREATE INDEX IF NOT EXISTS idx_visits_slug ON visits(slug);

CREATE TABLE IF NOT EXISTS feedback(
  slug   TEXT NOT NULL,
  reader TEXT NOT NULL,
  sid    TEXT NOT NULL,
  status TEXT NOT NULL CHECK(status IN ('done','blocked')),
  step   TEXT NOT NULL DEFAULT '',
  note   TEXT NOT NULL DEFAULT '',
  at     INTEGER NOT NULL,
  PRIMARY KEY(slug, reader),
  UNIQUE(slug, sid)
);
CREATE INDEX IF NOT EXISTS idx_feedback_slug ON feedback(slug, at DESC);

CREATE TABLE IF NOT EXISTS limits(
  k      TEXT PRIMARY KEY,
  window INTEGER NOT NULL,
  n      INTEGER NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_limits_window ON limits(window);

CREATE TABLE IF NOT EXISTS recovery(
  code_hash TEXT PRIMARY KEY,
  owner     TEXT NOT NULL,
  created_at INTEGER NOT NULL DEFAULT 0,
  last_used  INTEGER
);
CREATE INDEX IF NOT EXISTS idx_recovery_owner ON recovery(owner);

CREATE TABLE IF NOT EXISTS meta(k TEXT PRIMARY KEY, v TEXT NOT NULL);
```

`meta` 存 `schema_version=2`，供启动时判断是否需要迁移。

### 5.3 迁移方式

`init()` 保持幂等。对已有数据库按下列顺序处理：

1. 读 `meta.schema_version`，缺失视为 1。
2. 用 `PRAGMA table_info(<表>)` 检查列是否存在，缺列则 `ALTER TABLE ... ADD COLUMN ... DEFAULT 0`。
3. 时间戳为 0 的旧行批量回填：`UPDATE ... SET created_at = ? WHERE created_at = 0`，值取迁移时刻。
4. 写入 `schema_version=2`。

三个 SQLite 兼容性问题需要提前避开：

- 时间戳不用 `unixepoch()`。Ubuntu 22.04 自带 SQLite 3.37，该函数 3.38 才有。统一用 `CAST(strftime('%s','now') AS INTEGER)`。
- `ALTER TABLE ADD COLUMN` 的默认值必须是常量，所以先加 `DEFAULT 0` 再回填，不能直接写 `DEFAULT (strftime(...))`。
- 不在 DDL 里加 `CHECK(json_valid(data))`。旧版 SQLite 的 JSON1 编译选项不统一，校验放在 Python 层，避免启动即失败。

### 5.4 候选不单独建表的理由

拆成 `candidates` 表能支持跨运行统计，例如"某场景在所有运行中被判为适配的比例"。代价是 `rank()` 写入、发布读取、结果汇总三处都要改，还要给历史运行回填。

目前的查询需求都落在单次运行内：F1 一次取一条运行的至多三条候选，P3 的对照按运行逐条进行。因此保持内嵌，把候选对象字段在 `docs/DATA.md` 中固定下来：

```json
{"id":"interview","title":"...","author":null,"url":"/source/interview",
 "sourceType":"synthetic","evidence":"...","judgment":"适配",
 "reason":"...","unknown":"..."}
```

触发拆表的条件写清楚：需要跨运行统计候选命中率，或候选数超过 50 条导致单行 JSON 超过 100 KB。两条都不满足就不动。

### 5.5 数据不变量

这些规则由代码保证，测试逐条覆盖：

1. 归属：`/api/projects/:id/*` 必须 `projects.owner` 等于当前会话，否则返回 404，不区分"不存在"和"不属于你"。
2. 快照不可变：`cards.data` 发布后只读，撤回只改 `active`。
3. 版本单调：新版本为同项目最大值加一，`UNIQUE(pid,version)` 兜底。
4. 发布幂等：相同项目快照与卡片内容生成相同签名，且当前版本仍有效时，返回原版本。
5. 运行幂等：同项目同 `requestId` 返回首次结果。
6. 反馈唯一：同会话同卡片一份；同 `submissionId` 只落一条。
7. 计数口径：访问数等于 `visits` 行数，进入工具数等于 `opened=1` 的行数，自报完成数等于 `feedback.status='done'` 的行数。点击未反馈不计入完成。
8. 公开字段白名单：`GET /api/cards/:slug` 只输出卡片内容、工具名、入口、场景、版本、模式，不含 `pid`、`owner`、`signature`。

## 6. 身份与权限

### 6.1 开发者身份

现状是纯 Cookie 会话：`zhiyu_dev`，32 字节随机串，`HttpOnly; SameSite=Lax; Max-Age=2592000`。它满足"账号或会话边界"的要求，测试也验证了 A 无法访问 B 的项目。问题在于清 Cookie 就永久失联，评委换设备也进不去。

方案：在会话边界之上加恢复码，不引入密码体系。

- `POST /api/recovery` 生成新码，格式 `ZY-XXXX-XXXX`，字符集去掉易混的 `0/O/1/I`。明文只在响应里出现一次，库里存 SHA-256。
- 生成新码时旧码失效，一个工作区同一时刻只有一个有效码。
- `POST /api/recovery/claim` 校验后把当前会话的 Cookie 换成该工作区，返回原项目列表。
- 认领接口限 5 次/分钟/IP，失败只返回"恢复码无效"，不提示是否存在。

恢复码等价于口令。`docs/RUNBOOK.md` 写明：只发给评委和自己，不写进公开仓库，不贴在提交说明的正文里。

### 6.2 读者身份

保持匿名 Cookie `zhiyu_reader`，服务端只存随机串，不采集姓名、手机号、邮箱。会话用于访问去重与"同会话同版本一份反馈"，不作为自然人识别。README 与试用页都要说明这一点。

### 6.4 测试账号

给评委的不是账号密码，是一个可恢复的演示工作区：

- 部署时设 `ZHIYU_DEMO=1`，`init()` 写入一个示例项目、一张已发布卡片、两条反馈（一条完成、一条卡住）。
- 启动后生成恢复码，写入服务器上的 `/srv/zhiyu/var/DEMO_CODE`（权限 600），不进入 Git。
- P 在提交表单的"测试账号"栏填 `恢复码 + 站点地址 + 三步操作说明`。
- 工作台首页提供恢复码输入框，粘贴后调用 `/api/recovery/claim`，直接进入带数据的看板。

### 7.3 错误码

| 码 | 含义 | 典型场景 |
| --- | --- | --- |
| 400 | 参数不合法 | 字段超长、状态值非法、卡住未填步骤 |
| 403 | 来源或会话不合法 | Host 不在白名单、Origin 不匹配、会话缺失 |
| 404 | 不存在或无权访问 | 越权项目、已撤回卡片、未知接口 |
| 409 | 状态冲突 | 卡片版本不匹配、发布时项目已改、重复提交 |
| 413 | 请求体过大 | 超过 24 KB |
| 415 | 内容类型错误 | 非 `application/json` |
| 429 | 触发限流 | 读者写入超 30 次/分钟 |
| 503 | 存储不可用 | SQLite 忙、磁盘满、文件损坏 |

业务失败（匹配无结果、真实模式未配置）仍返回 200，用 `status` 与 `errorCode` 表达。这一点前端已经按此实现，不要改成 HTTP 错误码。

### 7.4 限流参数

| 桶 | 默认值 | 键 | 说明 |
| --- | --- | --- | --- |
| 读者写 | 30 次/分钟 | 客户端 IP | visit、open、feedback 合计 |
| 开发者写 | 120 次/分钟 | 客户端 IP | 保存、匹配、发布、撤回 |
| 读 | 600 次/分钟 | 客户端 IP | 页面与查询 |

`ZHIYU_TRUST_PROXY=1` 时取 `X-Forwarded-For` 首段作为客户端 IP，否则用 `client_address`。这一项必须与部署方式一致：漏配会把全站读者算成同一个 IP，30 次/分钟立刻误伤；错配则允许伪造请求头绕过限流。

窗口清理：每小时删除 `window < 当前分钟 - 10` 的行，避免表无限增长。

## 8. 阿里云部署方案

### 8.1 目标拓扑

```
Internet
   │  80 / 443
   ▼
阿里云安全组（仅放行 22、80、443）
   │
   ▼
Caddy（同机，自动证书、gzip、HSTS）
   │  127.0.0.1:4173
   ▼
python3 server.py（systemd 托管，User=zhiyu）
   │
   ├── /srv/zhiyu/var/zhiyu.sqlite3      持久数据（WAL）
   ├── /srv/zhiyu/backup/                每日备份
   └── /etc/zhiyu.env                    环境变量，权限 600
```

应用只监听回环地址，不直接暴露公网。这样 TLS、压缩、超时都由反向代理处理，Python 侧少一类攻击面。

### 8.2 主机与网络

已购主机的型号和地域由 P 提供，11/21 前确认。若尚未确定，按下列最低配置评估：2 vCPU、2 GiB 内存、40 GiB 系统盘、1 Mbps 带宽、Ubuntu 22.04 LTS。当前页面资源合计约 35 KB（`app.js` 23 KB、`styles.css` 9 KB、`index.html` 与 `mark.svg` 小于 2 KB），1 Mbps 下首屏在 1 秒内，够用。

安全组入方向只开三个端口：

| 端口 | 来源 | 用途 |
| --- | --- | --- |
| 22 | 本人固定 IP | 运维，禁止 0.0.0.0/0 |
| 80 | 0.0.0.0/0 | 跳转 HTTPS 与证书签发 |
| 443 | 0.0.0.0/0 | 正式访问 |

不使用非标端口。若最终退回 HTTP，再放行 4173，并在文档里注明原因。

### 8.3 域名、备案与 HTTPS

这是整个部署里唯一可能推翻方案的问题，单独说明。

按现行规定，绑定中国大陆地域服务器的域名需要完成 ICP 备案，未备案域名解析到大陆 IP 后，80/443 访问会被拦截。备案通常需要 7 至 20 个工作日，11/20 开始办赶不上 12/07。三条路线，按优先级排：

| 路线 | 条件 | 做法 | 风险 |
| --- | --- | --- | --- |
| A. 已备案域名 | 团队、学校或指导老师名下有备案域名 | A 记录指向主机，Caddy 自动申请 Let's Encrypt 证书 | 最低，优先争取 |
| B. 中国香港或海外地域 | 主机可换地域或新购轻量应用服务器 | 无需备案，同样用 Caddy 自动证书 | 成本增加约 30 元/月，延迟略高 |
| C. 纯 IP 访问 | 上述都不可行 | `http://<公网IP>:4173`，无 HTTPS，Cookie 不加 `Secure` | 地址栏显示"不安全"，观感差，但功能完整 |

决策点：11/21 20:00 前由 P 确认主机地域与域名归属，B2 在 11/22 前按对应路线出配置。不做"先上线再补备案"的打算。

### 8.4 反向代理选型

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| Caddy | 配置文件约 10 行，自动签发与续期证书，默认开 HTTP/2 | 限流插件需自行编译，本项目限流在应用层，不受影响 | 采用 |
| nginx + certbot | 团队更熟悉，生态成熟 | 证书续期要配 timer，配置项多，出错点更多 | 备选 |

两者都是 apt 安装，属于对主机的写操作，部署前需取得明确同意。

### 8.5 进程与目录

```
/srv/zhiyu/
├── app/                 git 工作副本
├── var/zhiyu.sqlite3    数据（属主 zhiyu:zhiyu，权限 640）
├── var/DEMO_CODE        演示恢复码（600，不进 Git）
└── backup/              备份（750）
```

systemd 单元：

```ini
[Unit]
Description=Zhiyu web app
After=network.target

[Service]
Type=simple
User=zhiyu
```

### 8.7 发布与回退

发布流程：

1. 本地 `python -m unittest` 全绿。
2. 打 tag：`v0.9.0-test`（11/26）、`v1.0.0-rc1`（12/04）、`v1.0.0`（12/06）。
3. 服务器 `git fetch && git checkout <tag>`，写 `BUILD` 文件，`systemctl restart zhiyu`。
4. `curl -s https://<域名>/api/health` 核对版本号。
5. 用无痕窗口跑一遍发布、读者、反馈、看板四步。

回退流程：

1. `git checkout <上一个 tag>`，重启，核对健康检查。
2. 从 v2 回到 v1 必须使用升级前的配套备份，见 DEPLOY.md。
3. 若某次迁移确实破坏兼容，停服，用最近备份恢复到 `var/`，再启动。
4. 回退后在工作群说明原因与影响范围，记录到 `docs/RUNBOOK.md`。

### 8.8 日志与监控

- 应用日志进 journald：`journalctl -u zhiyu -f`。不记录 Cookie、恢复码、反馈正文。
- 访问日志由 Caddy 写入 `/var/log/caddy/zhiyu.log`，字段含时间、方法、路径、状态、耗时、IP。
- 监控：cron 每 5 分钟 `curl -fsS https://<域名>/api/health`，连续 3 次失败发邮件或钉钉。阿里云云监控的站点监控可作为第二路。
- 磁盘：超过 80% 告警。SQLite 每周 `PRAGMA integrity_check`，结果写日志。

### 8.9 备份与恢复

指标：RPO 24 小时（每日 03:00 备份），RTO 15 分钟（恢复脚本加启动）。

备份脚本 `scripts/backup.sh`：

```bash
#!/usr/bin/env bash
set -euo pipefail
DB=/srv/zhiyu/var/zhiyu.sqlite3
OUT=/srv/zhiyu/backup
mkdir -p "$OUT"
STAMP=$(date +%F-%H%M)
sqlite3 "$DB" ".timeout 5000" ".backup '$OUT/zhiyu-$STAMP.sqlite3'"
sqlite3 "$OUT/zhiyu-$STAMP.sqlite3" "PRAGMA integrity_check;" | grep -qx ok
find "$OUT" -name 'zhiyu-*.sqlite3' -mtime +14 -delete
```

必须用 `.backup`，不能在服务运行时 `cp` 数据库文件。WAL 模式下直接复制会拿到缺少最新事务的副本，甚至撕裂页。

恢复演练（11/28 与 12/03 各一次）：

1. 取最新备份复制到 `/tmp/restore-test.sqlite3`。
2. `ZHIYU_DB=/tmp/restore-test.sqlite3 python3 server.py --port 4199`。
3. `curl -s 127.0.0.1:4199/api/health` 返回 200。
4. 对比项目数、卡片数、反馈数与线上一致。
5. 记录耗时与结果，写进 `docs/RUNBOOK.md`。

## 9. 安全与隐私

| 项 | 措施 |
| --- | --- |
| 传输 | TLS 1.2 以上，HSTS 一年；无 HTTPS 时明确告知风险 |
| 会话 | `HttpOnly`、`SameSite=Lax`、HTTPS 下加 `Secure`；30 天有效 |
| 越权 | 服务端校验归属，越权统一 404；前端隐藏不等于防护 |
| 注入 | 全部 SQL 使用参数绑定，不拼字符串 |
| XSS | CSP 已限制 `script-src 'self'`；卡片内容按文本渲染，不插入 HTML |
| 请求伪造 | 校验 `Origin`；写接口要求 `application/json` |
| 暴力尝试 | 恢复码认领 5 次/分钟；生成码 128 位随机 |
| 数据最小化 | 不采集姓名、手机号、邮箱；读者只有随机 token |
| 日志 | 不落 Cookie、恢复码、反馈正文；IP 保留 7 天 |
| 备份 | 权限 600，目录 750，不进入 Git；公开仓库不含演示码 |
| 依赖 | 仅标准库，无第三方包，无供应链风险 |

反馈正文由读者自述，可能包含个人信息。试用页与 README 注明"请勿填写真实姓名、联系方式等敏感信息"，开发者侧只展示原文，不做导出功能。

## 附录 C 术语

| 术语 | 含义 |
| --- | --- |
| 项目 | 开发者登记的一个 AI 工具及其输入、任务、输出、限制 |
| 运行 | 一次匹配请求，包含状态、错误码与候选列表 |
| 候选 | 一条知乎场景匹配结果，带判断、理由、证据与未知条件 |
| 卡片版本 | 一次发布产生的不可变快照，版本号按项目递增 |
| 会话 | 开发者 Cookie 或读者 Cookie，服务端只存随机串 |
| 恢复码 | 换回开发者工作区的凭据，可重复使用，生成新码后旧码失效 |
| RPO | 可接受的数据丢失窗口，本文为 24 小时 |
| RTO | 从故障到恢复服务的目标时间，本文为 15 分钟 |

## 附录 D 实施记录与偏差（2026-11-19，11-20 补 B2-3）

十项工作在本地完成。测试现为 65 组（`test_flow` 4、`test_deploy` 24、`test_matcher` 7、`test_publish` 9、`test_events` 17、`test_frontend_contract` 4），黑盒验收 30 项。香港 ECS 已完成明文直连部署（http://47.238.166.125:4173），黑盒验收 30/30 通过。以下为实施中与原方案的差异，以此为准：

1. 读限流改为进程内存计数，不写 `limits` 表，重启清零。写限流仍落库。原方案三档都落库，实测每次读请求写一次会放大写锁竞争。
2. 新增单进程 `WRITE_LOCK`。并发写时 SQLite 偶发 `attempt to write a readonly database`，串行后消失。代价是 5 并发写 p95 从约 60 ms 升到约 100 ms，仍在可接受范围。
3. 会话值校验从 32 至 64 字符放宽到 16 至 64。演示工作区的 `owner` 由 `uid()` 生成，长度为 24，原正则会把合法会话判为失效。
4. 索引从建表脚本移到迁移末尾。旧库缺 `updated_at` 时，先建索引会直接报 `no such column`，启动失败。
5. 恢复码可重复使用，直到生成新码；生成新码后旧码立即失效。它不是一次性凭据。
6. 备份与恢复脚本依赖 `sqlite3` 命令行，服务器需安装；Windows 下需 `cygpath` 转路径，脚本已处理。
7. 恢复码入口做成独立 `/recover` 页面，由后端直接提供，未改 `app.js`，避免与 F1 争用同一文件。
8. 写限流计数独立成一个事务，先提交再处理业务。最初把计数写在业务事务里，任何 400/409/429 都会随回滚把计数一起抹掉——实测 10 次非法请求后 `limits` 表仍为空，写限流从未生效，恢复码可被无限次爆破。代价是每个写请求多一次 `BEGIN IMMEDIATE`。
9. 部署配置补三处必要修正：`.env.example` 的 `ZHIYU_DB` 改为绝对路径（相对路径在 `ProtectSystem=strict` 下建库失败）；nginx 的 XFF 改用 `$remote_addr`（`$proxy_add_x_forwarded_for` 会把伪造值留在首位，绕过按 IP 限流）；systemd 增加 `PYTHONUNBUFFERED=1`。
10. B2-3 实施中修正一处计数缺陷：同一会话换 `submissionId` 再提交反馈，原实现被 `INSERT OR IGNORE` 静默丢弃却返回 200 与旧回执，读者以为改口成功、看板仍显示旧答案。改为返回 409，并补 `test_events.py` 17 组用例守住三列口径。
11. `runs` 增设 90 天留存（`server.prune`、`scripts/prune.py`），被 `cards.run_id` 引用的行永久保留，`visits` 与 `feedback` 不参与清理。原方案未定义清理策略，长期运行会把备份体积推到不可控。

10. 同一 `requestId` 不允许切换 `mode`。原实现命中缓存即返回旧运行，先跑合成再点「真实模式」会拿回 `synthetic success`，让人误判真实检索已通。现在模式不一致返回 409，要求换 `requestId`。
11. `cards` 增加 `run_id`、`candidate_id` 两列，记录这张卡来自哪次匹配、哪个候选。两列不进公开快照，只在所有者接口出现。
12. 新增只读接口 `GET /api/projects/:id/runs`，返回最近 50 条运行摘要。刷新页面后 `runId` 丢失仍能重新发布；列表不含候选全文，避免一次拉回所有草稿。
13. 旧版本链接保持可用，不被新版本顶掉。链接一旦发出去收不回；让读者看到「被换掉的版本」比让旧链接 404 更糟。要停某个链接必须显式撤回，且只影响那一个 `slug`。
14. 8.8 的监控告警落地为 `scripts/watch.sh` 加 `deploy/crontab`：连续 3 次失败告警一次、恢复补报一次、持续故障不重复推送；`503` 计入失败但文案指向数据库；磁盘按剩余低于 20% 报一次（等价于「超过 80% 告警」）；每周日 `--integrity` 对线上库跑 `integrity_check`。通知走 `--notify <命令>`（stdin 传消息），因为主机没有发信凭据；没配渠道时落 `var/watch.log`，预检 E6 报 `WARN`。

验证边界：systemd、Caddy/nginx、证书、cron 备份均未在 Linux 主机实跑；并发数据来自本地 Windows。上线后按 `docs/RUNBOOK.md` 复验，结果回填第 10.4 节的清单。
