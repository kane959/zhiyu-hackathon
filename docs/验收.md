# 验收

分三层，从「代码对不对」到「线上能不能用」，每层都有可复现的命令和明确的通过判据。前两层不需要人判断，第三层才需要眼睛。

要照着一步步做的版本（含每步在哪台机器、具体命令、期望输出）见 [验收-操作手册.md](验收-操作手册.md)；本文是判据与失败定位。

## 第一层：代码验收（3 分钟，只要一台装了 Python 的机器）

以下命令都在**项目根目录**执行（本例为 `D:\湾区S3黑客松`）。路径是相对项目根写的，在 `C:\WINDOWS\system32` 之类的目录下运行会报 `No such file or directory`。

```powershell
cd D:\湾区S3黑客松
```

### 1.1 一条命令看总线

```powershell
python scripts\accept.py
```

要留一份日志给队友：

```powershell
python scripts\accept.py | Tee-Object -FilePath docs\accept-20261119.log
echo $LASTEXITCODE
```

判退出码用 `$LASTEXITCODE`，不要用 `$?`——PowerShell 5.1 对原生程序加 `2>&1` 时，即使成功也会把 `$?` 置为 False。

它会自己起一个临时实例（临时库、随机端口），跑 30 项黑盒检查，然后销毁。**不经手你的任何数据**。

通过时最后三行长这样：

```
====================================================
通过 30/30，耗时 1.1s
全部通过。
```

退出码 0 才算通过。任何一项失败会打印 `[失败] 名称  原因`，退出码 1。可以塞进 CI，也可以把这段输出直接贴给队友。

### 1.2 单元与集成测试

```powershell
python -m unittest -v test_flow test_deploy
```

预期 `Ran 14 tests ... OK`。

这两条的分工别搞混：`unittest` 测的是函数级行为（迁移、限流计数、Cookie 属性），`accept.py` 测的是 HTTP 级行为（真实请求、真实 Cookie、真实 403）。两边都绿才算代码过关。

### 1.3 30 项分别验了什么

| 组 | 项数 | 验的事情 |
|---|---|---|
| A 可用性 | 3 | 健康检查返回 `ok/db/version`、首页与 `/recover` 能打开、健康检查不依赖 Cookie |
| B 隔离 | 4 | 两个工作区互相看不见、直接猜 URL 访问别人项目返回 404 |
| C 匹配发布 | 8 | 候选带判断、相同 `requestId` 幂等、切换模式被拒 409、真实模式明确报未配置、发布出 v1、相同快照不升版本、公开卡片不泄露内部字段、卡片可追溯到来源运行 |
| D 事件反馈 | 7 | 重复 visit/open 不重复计数、反馈幂等、同会话换 `submissionId` 再提交 409、`blocked` 缺步骤返回 400、看板四项统计对得上、版本不符 409、撤回后读者 404 |
| E 输入防护 | 4 | 伪造 Host 403、非 JSON 415、超 24 KB 413、跨站 Origin 403 |
| F 恢复码 | 4 | 格式正确、换浏览器能拿回项目、轮换后旧码失效、连续试错触发 429 |

**这一层跑不过就不该往主机上传代码。** 尤其是 C 组和 D 组：它们覆盖的是评委当天会点的路径。

## 第二层：主机验收（部署之后，约 20 分钟）

**前提：代码已经在那台主机上跑起来**，也就是按 `docs/DEPLOY.md` 做完 `git clone`、`systemd` 启动、反代转发这三步。域名只是个门牌号，门后面没人，验收就无从谈起——没部署时 `https://域名` 通常返回 404、备案拦截页或别的站点，`accept.py` 会在第一项就报「这个地址后面不是知遇」。

部署完，对这个地址再跑一次同一套检查：

```bash
python3 scripts/accept.py --base https://你的域名
```

`--base` 的意思只是「验收哪个地址后面跑着的实例」，不是线上专用。本机起了一个实例也可以这样验：

```bash
python server.py --port 4173
python scripts/accept.py --base http://127.0.0.1:4173
```

它会在目标地址上真的建一个测试工作区、发一张卡、写一条反馈，**不会自动清理**。验收完按第 4 节收尾。

如果这一步报的是「不可达」或「不是知遇」，问题在部署和反代，不在功能，先回去看 `docs/DEPLOY.md` 第 5、6 节。

`--base` 里的 `https://你的域名` 要换成真实域名。占位符、中文域名、缺 scheme 三种写法会在发请求前被脚本拒绝，各给一句说明；不会跑到一半才报错。

脚本对回环地址会自动绕开 `HTTP_PROXY`，在设了代理的机器上验收本地实例不需要额外参数。

### 2.1 部署专项（脚本覆盖不到的部分）

| # | 检查 | 命令 | 通过判据 |
|---|---|---|---|
| 1 | 服务自启 | `systemctl is-enabled zhiyu && systemctl is-active zhiyu` | 两个都返回 `enabled` / `active` |
| 2 | 端口不裸奔 | `ss -lntp`（看 4173 那一行） | 只监听 `127.0.0.1:4173`，不是 `0.0.0.0` |
| 3 | HTTPS 与跳转 | `curl -I http://域名` 和 `curl -I https://域名` | 80 返回 301，443 返回 200，证书主体是域名 |
| 4 | HSTS | `curl -sI https://域名`（看响应头） | 有 `Strict-Transport-Security: max-age=31536000` |
| 5 | 真实 IP 限流 | 看 `journalctl -u zhiyu -n 50`，或临时开 `ZHIYU_ACCESS_LOG=1` | 日志里的 IP 是你的公网 IP，不是 `127.0.0.1` |
| 6 | 版本号对得上 | `curl -s https://域名/api/health` | `version` 等于 `git rev-parse --short HEAD` 拼出来的那个串 |
| 7 | 重启后数据还在 | `systemctl restart zhiyu` 后再跑一遍 `accept.py --base` | C 组能读到重启前建的项目 |
| 8 | 备份能产出 | `sudo -u zhiyu /srv/zhiyu/app/scripts/backup.sh` | 输出 `backup ok`，`/srv/zhiyu/backup` 下有新文件 |
| 9 | 备份能恢复 | `scripts/restore-check.sh /srv/zhiyu/backup/<文件>` | 输出 `restore rehearsal ok`，五类记录计数与备份一致 |
| 10 | 会话不串 | 用两个浏览器分别建项目 | 互相看不到（就是 accept.py 的 B 组，这里人工复核一次） |

第 8、9 项是 B2-4 明确要求的「重启后数据仍在，备份可恢复到独立副本」，**必须有输出截图或日志，不能只说做过**。

### 2.2 第二层的通过判据

必须 27/27，且 2.1 的十项全过。

有一项可以放过、但要记录：第 5 项在没开 `ZHIYU_ACCESS_LOG` 时看不到访问日志。这不影响限流正确性（`accept.py` 的 E 组已证明按 IP 分桶生效），记为「未观测」而不是「通过」。

## 第三层：人工验收（10 分钟，需要真浏览器）

只在本地或线上各做一次，覆盖自动脚本看不见的东西。

| # | 做什么 | 看什么 |
|---|---|---|
| 1 | 手机打开一张试用卡 | 不横向滚动，按钮点得到，正文不挤成一团 |
| 2 | 打开 `/recover` | 样式正常（不是裸 HTML），输入框能打字 |
| 3 | 在 A 浏览器生成恢复码，在 B 浏览器粘贴认领 | B 能看到 A 的项目和卡片 |
| 4 | 开发者看板 | 访问、点击、完成三个数字与实际操作次数一致 |
| 5 | 浏览器的控制台 | 没有红色报错，没有 `Content Security Policy` 拦截 |
| 6 | 断网后随便点一下 | 给出可读的提示，不是白屏或无限转圈 |
| 7 | 手机上点一次「试跑访谈稿示例」 | 页面跳到卡片，不出现 `crypto.randomUUID is not a function` |

第 7 项是 11/20 真机验证加的。`crypto.randomUUID()` 只在 secure context（HTTPS 或 localhost）可用，明文 IP 访问时原生方法缺失——**HTTP 状态全是 200，肉眼看像「网络慢」**。已在 `app.js` 顶部加兜底（用 `crypto.getRandomValues` 补一个），明文 IP 下也不会报错；`test_frontend_contract.py` 有 4 组测试守着这条约定。若这一条挂了，先看 `app.js` 顶部的兜底是否被删，再看浏览器是不是缓存了旧文件（静态资源 `max-age=300`，强刷或清缓存）。

第 5 项特别重要：服务端下发了严格的 CSP（`script-src 'self'`）。如果 F1/F2 后续往 `index.html` 里加了内联 `<script>` 或 `style="..."`，页面会静默失效——样式不生效、按钮没反应，但 HTTP 全是 200。自动测试发现不了，只能靠控制台。

## 不通过怎么办

按失败组直接定位，不用从头翻：

| 失败位置 | 先看哪里 |
|---|---|
| A 组 403 | `ZHIYU_HOSTS` 有没有把域名加进去；反代有没有传原始 `Host` |
| C 组 409 | 项目在匹配之后被改过。这是预期行为，重新匹配再发布 |
| D 组计数不对 | `visits` 表按 `(slug, reader)` 去重，换浏览器就会多一条。不是 bug |
| E 组伪造 Host 没拦住 | 只在 `--base` 模式下出现，说明实例的 `ZHIYU_HOSTS` 配得过宽 |
| F 组 429 提前出现 | 同一 IP 一分钟内已经试过。等一分钟重跑 |
| 全部 503 | 看 `journalctl -u zhiyu -n 100`，多半是 `ZHIYU_DB` 路径不可写 |

## 验收完的收尾

默认在独立临时库运行，结束后自动清理。`--base` 只对专门的测试实例使用；不要按项目名称批量删除共享库的数据。

## 交出去时要带的三样东西

1. `python scripts/accept.py` 的完整输出（27/27）。
2. 2.1 第 8、9 项的备份与恢复实跑输出。
3. 第三层第 1、3 项的手机截图。

这三样凑齐，P 就不需要再问你「到底能不能用」。
